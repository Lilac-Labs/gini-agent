# ADR: Docker + Xvfb Deployment

## Decision

Gini ships a container image (`Dockerfile`, `docker-compose.yml`, `docker/entrypoint.sh`) that runs one instance's full runtime gateway + Next.js control plane headless on a server, with the agent's browser driven as a **real headed Chromium under a virtual X display (Xvfb)**.

The runtime needs three behaviors that differ from a host install. Each is a single env-gated seam resolved in `packages/runtime/src/lib/container-env.ts`, and each **defaults to the exact historical host behavior** when its env var is unset, so a non-container run is byte-for-byte unchanged:

- **`GINI_BIND_HOST`** (default `127.0.0.1`). The gateway's `Bun.serve` binds this host (`packages/runtime/src/server.ts`). A container sets `0.0.0.0` so Docker's published-port forwarding — which targets the container's `eth0`, not loopback — reaches the gateway. **Security: this required moving the local-operator trust decision from the Host header to the real socket peer.** On the historical loopback-only bind, `isLoopbackHost(Host)` was a safe proxy for "the local operator" because the bind itself guaranteed only the host's own loopback could open the socket. On a non-loopback bind that guarantee is gone: a remote peer reaches the socket through Docker's NAT and can forge `Host: localhost`, which would otherwise hand it the loopback bypass (the web-bound trust lane and the self-describe banner keyed on a loopback Host). The fix gates every loopback-Host trust on `isLoopbackPeer(server.requestIP(...).address)` — the kernel-reported peer, never a forgeable header (`X-Forwarded-For`/`Host`). The handler returned by `createHandler` takes the peer address as an optional second argument (`server.ts` supplies it; it defaults to loopback when absent, so the loopback-bind path and in-process callers are unchanged). A forged loopback Host arriving from a non-loopback peer therefore gets **no** bypass and is refused (401 for `/api/*`, 404 for pages) — verified by `packages/runtime/src/http-nonloopback-bind.test.ts`. The inner Next.js child stays loopback-bound and is reached only through the gateway reverse proxy (see [Gateway Reverse Proxy](gateway-web-reverse-proxy.md), [BFF Trust Boundary](bff-trust-boundary.md), and [Owner-Token-Only Authentication](owner-token-auth.md)).
- **`GINI_BROWSER_HEADLESS`** (default `true`). The spawned-session provider in `packages/runtime/src/tools/browser.ts` passes this to `launchSpawnedChrome`. A container running Xvfb sets `false` so Chrome launches **headed** against `DISPLAY=:99`. A real headed Chrome under Xvfb presents fewer automation signals than `--headless=new`, complementing the stealth identity (see [Browser Stealth Identity](browser-stealth-identity.md)).
- **`GINI_CHROME_NO_SANDBOX`** (default off). When set, `containerChromeArgs` appends `--no-sandbox` and `--disable-dev-shm-usage` to the launch (in `packages/runtime/src/tools/chrome-launch.ts`, after the shared `CHROME_LAUNCH_ARGS`). Chrome's setuid/namespace sandbox can't initialize in a default container, and the default 64MB `/dev/shm` is too small for Chrome's shared-memory segments. Neither flag is web-observable, so the stealth identity is unaffected.

The entrypoint (`docker/entrypoint.sh`) starts `Xvfb :99` only when the browser will be headed, polls for the display socket, then `exec`s the gini CLI so `SIGTERM` from `docker stop` reaches the runtime directly for its graceful drain. `tini` is PID 1 (image `ENTRYPOINT`) to reap Chromium's orphaned children.

## Context

The runtime was loopback-only by construction: `Bun.serve` hard-coded `hostname: "127.0.0.1"`, the browser hard-coded `headless: true`, and the launch carried no container sandbox flags. All three are correct for a host install and wrong for a container — but the security model already tolerates a wider bind, because trust is decided on the `Host` header at the single front, not on the bind interface. That made an env-gated bind host the minimal, safe change rather than a new trust lane.

Headed-under-Xvfb (rather than `--headless=new`) is the deliberate choice because this codebase already invests heavily in not looking like automation (branded Chrome, cleared `navigator.webdriver`, a "Headless"-stripped UA — see [Browser Stealth Identity](browser-stealth-identity.md)). Running a genuinely headed browser against a virtual display removes the residual headless tells for free; Xvfb is the standard way to give a headed browser a display on a server with no GPU or monitor.

Build-time specifics that the image must get exactly right (verified against the live base image, June 2026):

- The base `oven/bun:1.3.14-debian` is **Debian 13 "trixie"**, so the Chromium runtime libraries use the **t64-suffixed** package names from the 64-bit-time ABI transition (`libasound2t64`, `libatk1.0-0t64`, `libatk-bridge2.0-0t64`, `libatspi2.0-0t64`, `libcups2t64`, `libglib2.0-0t64`); the pre-trixie names do not resolve.
- `onnxruntime-node` (embeddings/reranker/STT) needs `libgomp1`, which the slim base omits.
- The `gini-relay` dependency is pinned `git+ssh://git@github.com/...` but the repo is public; the build rewrites ssh→https for github so `bun install` clones it with no SSH key.
- The web control plane serves a **sha-keyed production bundle** (see [Sha-Keyed Production Serving](web-production-serving.md)), and `resolveWebProdDistDir` runs `git rev-parse --short=12 HEAD` at **both** build and runtime. A worktree's `.git` is an unusable pointer file and the slim base has no `git`, so the image installs `git` and `git init`s a fresh in-container repo; the build keys the bundle to that committed HEAD so the runtime finds it.

## Tradeoff

- **Image size.** Bundling Playwright's Chromium, the CJK font set, node_modules, and the web prod build produces a multi-gigabyte image. This is the cost of a self-contained "first browser use is instant, no font tofu, prod-mode web on boot" image. Operators who don't need CJK or who accept the on-demand Chromium download can trim the apt font list and drop the `playwright install` layer.
- **`--no-sandbox` as the default container posture.** The image runs as the non-root `bun` user but still disables Chrome's sandbox. This is acceptable because the agent drives the operator's own trusted automation, the sandbox can't initialize in a default container anyway, and the alternative (a custom seccomp profile permitting `clone`/`setns`/`unshare`, or `--cap-add=SYS_ADMIN`) is heavier and operator-specific. An operator who runs the container with such a profile can unset `GINI_CHROME_NO_SANDBOX` to restore the sandbox.
- **In-container `git init`.** The image carries a synthetic single-commit repo rather than the real history, purely so the sha-keyed prod-serving fast path works. `gini update`'s `git fetch origin` is meaningless in the container (the remote is the synthetic repo), so in-container self-update is not supported — operators update by rebuilding the image, which is the correct container workflow anyway. `.dockerignore` ships the repo's `.gitignore` so `git add -A` skips `node_modules` (hashing it made the snapshot commit ~72s / ~888 MB); the runtime reaches the repo as the `bun` user, so the build sets `git config --system --add safe.directory /app` — without it `git rev-parse` hits a dubious-ownership error and the web silently drops to `next dev`.
- **Build cost is easy to regress.** Two Dockerfile choices keep the build from ballooning; a future edit should preserve them. (1) The final ownership step chowns the `/app` worktree to `bun` but PRUNES `node_modules` — bun only reads/executes it, so a recursive `chown -R /app /opt/ms-playwright` needlessly duplicates ~3.5 GB into a fresh layer and adds minutes. (2) The guest-init apt install (`iproute2`/`procps`/…) sits ABOVE the source `COPY` so a source-only edit reuses the cached layer instead of re-running apt. Build under **BuildKit** (the `docker-buildx` plugin) rather than the deprecated legacy builder: it removes the ~10 s/layer commit tax and makes the `--mount=type=cache` on `bun install` work, so a dependency bump re-resolves from cache instead of re-downloading ~1.9 GB.

## Consequences For Coding Agents

- The three container seams live in one module, `packages/runtime/src/lib/container-env.ts`, each a pure function of an injected env bag. New container-only behavior should add a seam there with a host-preserving default, not branch on `process.env` inline at a call site.
- The call sites are exactly three: `packages/runtime/src/server.ts` (`resolveBindHost`), `packages/runtime/src/tools/browser.ts` spawned-session provider (`resolveBrowserHeadless`), and `packages/runtime/src/tools/chrome-launch.ts` `buildOptions` (`containerChromeArgs`). The launch args are appended after `CHROME_LAUNCH_ARGS` so the stealth flags and `--remote-debugging-port` are never displaced.
- The Dockerfile pins `oven/bun:1.3.14-debian` (trixie). Bumping the base across a Debian major requires re-checking the t64 package names — a Debian 12 (bookworm) base needs the non-t64 names.
- The web prod build step uses `cd packages/web && bun run build` (matching `startWeb` in `packages/runtime/src/cli/process.ts`), not a leading `--cwd` flag — `bun run` takes the script name as its first positional. The step asserts `packages/web/.next-prod-<sha12>/BUILD_ID` exists rather than trusting the exit code.

## Acceptance Checks

- `resolveBindHost` returns `127.0.0.1` when `GINI_BIND_HOST` is unset/empty and the explicit value otherwise; `resolveBrowserHeadless` returns `true` unless `GINI_BROWSER_HEADLESS` is an explicit falsy value; `containerChromeArgs` returns `[]` unless `GINI_CHROME_NO_SANDBOX` is truthy, then `["--no-sandbox", "--disable-dev-shm-usage"]`. `packages/runtime/src/lib/container-env.test.ts` covers these at 100% line/function coverage.
- With container env unset, `packages/runtime/src/tools/chrome-launch.test.ts` and `packages/runtime/src/tools/browser.test.ts` pass unchanged (no new launch args, browser still headless).
- `docker build` against `oven/bun:1.3.14-debian` resolves every apt package (t64 names), installs Chromium via `playwright-core/cli.js install chromium`, and produces `packages/web/.next-prod-<sha12>/BUILD_ID`.
- A booted container answers `GET /api/status` on the published gateway port and serves the web control plane; `gini status` inside the container reports the instance healthy.
- Inside the container, `launchSpawnedChrome({ headless: false })` under `DISPLAY=:99` navigates a page and captures a non-blank screenshot — proving headed Chrome renders under Xvfb.
- A chat turn through `POST /api/chat/<id>/messages` completes against the echo provider, confirming the gateway's full request path works over the `0.0.0.0` bind.
- With the gateway bound `0.0.0.0` and a port published, a request from off-host carrying a forged `Host: localhost` and **no** owner bearer is refused (a page nav 404s; a `/api/*` call 401s) — it is NOT admitted as the loopback operator. A genuine in-container loopback request (peer `127.0.0.1`) on the same path is still admitted. `isLoopbackPeer` and the gated banner/trust lanes are covered by `packages/runtime/src/http-nonloopback-bind.test.ts`, and the existing loopback/trusted-front behavior by `packages/runtime/src/http.test.ts`.
